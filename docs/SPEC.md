# SPEC — 공연 티켓 예매 시스템

## 1. 한 줄 정의
공연(Event)의 좌석을 회원이 예매하는 웹 서비스. 인기 공연 예매 오픈 시
다수 사용자가 같은 좌석에 동시에 몰리는 상황을 안전하게 처리하는 것이 핵심.

## 2. 왜 만드는가 (학술 목표)
대학 DB 과목에서 배운 5개 개념을 **실제 동작과 측정 데이터로 증명**하기 위한 프로젝트다.
- 데이터베이스 설계
- 정규화
- 인덱싱
- 트랜잭션
- 동시성 컨트롤

각 개념을 어디서 어떻게 보여줄지는 `CONCEPTS.md` 참조. 기능의 화려함보다
"이 다섯 가지를 명확히 시연·설명할 수 있는가"가 우선순위다.

## 3. 핵심 도메인 흐름
1. 회원이 공연을 고르고 좌석맵에서 좌석을 선택한다.
2. 좌석을 일정 시간 **HOLD**(임시 점유)한다 — 만료 시 자동 해제.
3. 결제하면 HOLD가 **SOLD**로 확정된다 (트랜잭션: 예매·좌석상태·결제기록 원자적 처리).
4. 같은 좌석에 동시 요청이 오면 한 명만 성공한다 (동시성 컨트롤).

데모 시나리오: "예매 오픈 시각에 좌석 1개로 수백 건 동시 요청" → 락 없으면 중복판매,
락 있으면 정확히 1건만 성공.

## 4. 제출물 (Deliverables)
- GitHub 레포지토리 (코드 + 문서 + 마이그레이션 + 부하테스트 스크립트)
- 결과물 설명 PPT (증거물은 CONCEPTS.md의 산출물 목록 기반)
- 라이브 서비스 주소

## 5. 범위 밖 (Out of scope) — 의도적으로 안 함
- 실제 결제 PG 연동 (결제는 모의 처리로 충분)
- 복잡한 추천/검색, 소셜 기능
- 마이크로서비스 분리, 캐시 서버(Redis) 등 (동시성은 DB 레벨로 증명하는 게 과목 취지)
- 고도화된 프론트엔드 (좌석맵이 보일 정도면 충분)

## 6. 배포 타깃
- DB: Neon (무료, scale-to-zero / 콜드스타트 1~2초)
- 앱: Render 무료 티어 (15분 미사용 시 spin down, 첫 접속 30~60초 지연)
- 제출/발표 직전에는 콜드스타트 방지를 위해 미리 워밍업할 것
